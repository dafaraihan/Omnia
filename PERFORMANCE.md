# Performance Guide and Measurement Plan

> **Automated-validation policy:** Follow the repository-root `AGENTS.md`. Instructions below that call for automated test targets, suites, fixtures, or scripts are historical and superseded; use builds, static checks, and focused manual evidence instead.

## Status and interpretation

Omnia does not yet have a recorded performance baseline. No repository artifact currently establishes launch latency, visible-content latency, interaction response, frame rate or hitch behavior, memory use, energy use, network cost, image-decoding cost, or playback startup time. The numbers below are **proposed targets**, not measurements of the current app and not promises for every provider or network.

Static inspection can reveal work that may become expensive; it cannot prove a regression. A change may be described as faster, lower-memory, or lower-energy only after before-and-after traces are captured on the same real supported hardware, OS, build configuration, data set, network profile, power state, and scenario. Simulator results and Debug builds are diagnostic only.

Keep each accepted baseline with the commit SHA, Xcode and OS versions, device model, build configuration, scenario/fixture, network conditions, Low Power Mode and thermal state, run count, raw Instruments trace or XCTest result, median, p90, and variance. Use a Release build and at least 10 runs after one untimed warm-up; compare distributions rather than the best run. Re-record when supported hardware, rendering, persistence, networking, or a major OS version changes.

Some evidence used in this audit, including `OmniaTests` fixtures and newly added playback files such as `MPVPlayerController.m`, is present in the user's current working snapshot but is not committed in this documentation branch's history. Findings below identify that provenance where it matters. Snapshot presence supports static inspection only; an uncommitted fixture or implementation cannot back an enforceable performance gate.

## Measurement scenarios

Once a profile is activated, use its committed, versioned, non-secret fixtures and repeatable script:

1. **Launch:** first install, force-quit relaunch, and relaunch after memory pressure; measure first frame and `homeContentReady` independently.
2. **Home:** empty caches, default metadata route, fixed network profile, then a warm-cache repeat. Scroll every shelf end to end.
3. **Search and catalog:** type a fixed query quickly, replace it, leave the screen during the request, and load three pages. Verify cancellation and request uniqueness.
4. **Detail and images:** open a fixture with backdrop, poster, episodes, videos, and credits; cycle Home -> detail -> Home three times.
5. **Playback:** for pre-gate diagnosis, a local fixture is present in the current working snapshot at `OmniaTests/Fixtures/multi-track.mkv`; it is not committed in this documentation branch and cannot establish a gate. An active profile must name a committed local fixture for engine cost and a versioned controlled HTTPS fixture for transport cost. Exercise pause, seek, track changes, background/foreground, and stop.
6. **Power:** repeat browse and playback unplugged at fixed brightness, once normally and once with Low Power Mode. Begin only at nominal thermal state.

Name signposts consistently: `appLaunch`, `homeContentReady`, `catalogPage`, `search`, `imageFetch`, `imageDecode`, `sourceResolve`, `playbackStartup`, `firstAudio`, `firstVideoFrame`, and `progressPersist`. Never include URLs, query text, tokens, or title names in signpost metadata.

## Subsystem guidance

### Requests, cancellation, and concurrency

- Give the metadata and add-on layers one request coordinator. Key in-flight work by normalized method, URL, non-secret body identity, provider route, and page; attach multiple consumers to one task and cache only successful responses.
- Cancel obsolete searches, destination-owned page loads, image work, and startup work when their owner disappears or input changes. Cancellation must propagate to `URLSessionTask`, and stale completions must not mutate observable state.
- Bound independent catalog operations rather than launching every shelf and page simultaneously. Start content required above the fold first, then fill the remaining shelves with a small configurable limit. Determine the limit from Network and Power traces, not intuition.
- Make a configured `URLSession` owner explicit for metadata, add-ons, and artwork. Define timeout, connectivity, cache, cookie, cellular/constrained-network, metrics, and test-injection policy once. Do not infer caching merely because the shared session is used.
- Separate transport deduplication from semantic cache ownership. Record memory/disk capacity, freshness, revalidation, eviction, user/account partitioning, and invalidation on route or credential changes. Never cache credentials or authorization-bearing responses in a shared public bucket.

### Images and SwiftUI

- Replace screen-level `AsyncImage` policy with an artwork pipeline that shares fetches and cache entries across poster, backdrop, still, logo, and avatar consumers. Include representation and target pixel size in the decoded-cache key.
- Read image metadata and create a thumbnail near `viewSizeInPoints * displayScale`; use Image I/O thumbnail options instead of decoding a provider-sized image and resizing afterward. Decode and prepare bitmap data off the main actor, then publish the final image on the main actor.
- Cap encoded and decoded caches independently and react to memory pressure. Cancel off-screen work; prefetch only the next small visible window and disable speculative work under Low Power Mode or elevated thermal state.
- Preserve stable domain identity in `ForEach` and lazy containers. Avoid index IDs and `.id(...)` churn for network-backed content; isolate rapidly changing playback/progress state from large grids. Use the SwiftUI instrument's update groups and cause graph before refactoring view structure.

### Actor isolation and persistence

- Keep observable UI mutation on `@MainActor`, but move parsing, sorting, canonicalization, JSON coding, image decode, and database/file I/O to isolated workers with `Sendable` results. Actor annotations alone do not prove that underlying work is off-main; verify thread samples.
- Treat `UserDefaults` as small-preference storage, not an ever-growing media database. The current code forces progress emission only through `stop`, including the `stop` call made before a new `start`; it has no general background or termination persistence hook. Batch playback progress mutations, encode a snapshot away from the main actor, and write no more often than the measurement-backed interval. Add explicit background/termination flushes only as a future implementation requirement, then measure those paths before relying on them. For a growing library, use an atomic file or database with incremental updates.
- Preserve crash consistency: coalesce by media ID, serialize writes through one owner, and ensure an older async encode cannot overwrite newer state. Measure bytes and write frequency as well as duration.

### Playback, power, and thermal behavior

- Prefer player/event callbacks for pause, duration, tracks, errors, first frame, and end-of-file. Use a low-frequency periodic observer only for visible progress, suspend it when paused/backgrounded/off-screen, and avoid reconstructing complete track arrays on every tick.
- Signpost source resolution separately from engine startup and first frame. A provider delay, network delay, decoder delay, and renderer delay require different actions.
- Compare the current macOS OpenGL path with a supported Metal/libmpv integration before migrating; deprecation is a maintenance and future-performance risk, not proof that current rendering is slow.
- Observe `ProcessInfo.isLowPowerModeEnabled` and thermal-state changes. Reduce speculative prefetch, image concurrency, animation, polling, and nonessential refresh at fair/serious states; stop optional work at critical. Playback correctness and user-initiated controls remain higher priority than prefetch.

## Profiling recipes

### Time Profiler and points of interest

Build Release with symbols, install on the reference device, choose Product > Profile, and start with App Launch or Time Profiler. Record one scenario at a time. Mark the signpost interval as the inspection range; use separate-thread and inverted call trees, hide system libraries only after checking blocking stacks, and inspect main-actor time, waits, JSON transforms, image decode, and persistence. Export the `.trace` with the run metadata. Repeat after a change under identical conditions.

### SwiftUI, Hangs, and Hitches

Use the SwiftUI template on toolchains that provide it, with Time Profiler and Hangs/Hitches enabled. Perform the fixed 30-second scroll and playback-control scripts. Inspect update groups, long body/platform updates, cause graphs, hitch duration, and hitch-time ratio. Confirm identity or observation changes reduce the relevant update count; do not infer smoothness from average frame rate.

### Allocations, VM Tracker, and Leaks

Measure first Home, a fully scrolled catalog, three detail cycles, and playback separately. Mark generations after stable states, inspect persistent growth and large image/pixel buffers, then run Leaks after exercising navigation and stop/deinit. Record physical footprint, dirty memory, allocation categories, decoded-cache occupancy, and post-cycle retained growth. A clean Leaks run does not prove bounded memory.

### Network and HTTP traffic

Use Network/HTTP Traffic with a fixed route and network condition. Clear only the app-owned test caches before the cold run; preserve them for the warm run. Count request attempts, redirects, fallbacks, cancellations, bytes, status, cache source, DNS/connect/TLS, time to first byte, and completion. Group by normalized request key to expose duplicates. Redact authorization, query terms, signed URLs, and provider credentials before sharing a trace.

### Energy Log or Power Profiler

Prefer Power Profiler on supported real devices; otherwise use Energy Log. Unplug, fix brightness, start nominal and idle, and record the exact browse/playback duration. Correlate power with CPU/GPU, display, wakes, network, playback polling, thermal state, and signposts. Repeat in Low Power Mode. Charging traces, simulator scores, and unlike devices are not comparable.

### XCTest metrics

Use UI/XCTest automation to drive the same stable launch, navigation, scroll, and playback flows on every run. Use `XCTOSSignpostMetric` to measure the app's signposted intervals; it does not drive the interaction itself. Use `measure(metrics:options:block:)` with `XCTClockMetric`, `XCTCPUMetric`, `XCTMemoryMetric`, `XCTStorageMetric`, and `XCTApplicationLaunchMetric` where each platform/toolchain supports them. Keep fixtures committed, local, and deterministic; isolate setup from measurement and use the exact iteration count declared by the active profile. Accept a baseline only after reviewing variance and profiling outliers. Do not loosen tolerance or re-record a baseline merely to turn CI green.

### Xcode Organizer and MetricKit

For App Store/TestFlight builds, review Organizer by version, device, OS, median, and high percentile for launch, hangs/hitches, memory, and battery impact. Integrate the MetricKit API supported by the deployment toolchain, retain its manager/subscription for process lifetime, and ingest daily metrics and diagnostics without user content. Field data is aggregated and can be absent at low volume; it complements controlled Instruments traces rather than replacing them. Alert on statistically credible regressions against the previous stable release and retain symbol archives.

## Review gate

A performance pull request must state the affected `PERF-*` item, hypothesis, target, hardware and conditions, before/after distributions, trace locations, functional tests, and tradeoffs. Reviewers should reject claims based only on static code, Simulator runs, Debug builds, a single sample, or an updated baseline without diagnosis.
